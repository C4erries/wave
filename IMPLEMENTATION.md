# Wave — описание реализации для текстовой части

Этот документ описывает всё, что реализовано в системе Wave начиная с базового
коммита (stage on1: SDK-субмодуль + синусный генератор + codec). Предназначен
для агента, который пишет текстовую часть курсовой работы.

---

## Контекст и назначение системы

Wave — система потоковой обработки сигналов реального времени. Исходно
создавалась как программная обвязка для осциллографа PicoScope 5000a, но
развита до универсальной платформы: любой источник сигнала публикует блоки
отсчётов в брокер сообщений, независимые операторы подписываются на нужные
топики, обрабатывают данные и публикуют результат в новые топики, веб-интерфейс
визуализирует любой топик в реальном времени.

Основная архитектурная идея: **операторы полностью stateless и не знают друг о
друге** — они соединяются только через именованные топики брокера. Добавить
новый шаг обработки — значит запустить ещё один процесс.

---

## 1. Брокер сообщений (Wave-MQ)

Брокер реализован отдельно (Go, подмодуль wave-mq). Система использует его как
чёрный ящик. Каждый топик — это лог с партициями. Производители записывают блоки
данных, потребители читают с любого offset, offset фиксируется по consumer group.

Брокер предоставляет:
- TCP API на порту 7912 — для Python-клиентов (SDK)
- HTTP API на порту 8090 — для UI и мониторинга (список топиков, offset'ы,
  consumer groups, throughput)
- MQTT на порту 1883 — не используется в текущей реализации

---

## 2. Бинарный формат кадра (codec)

Все топики используют единый бинарный формат. Это позволяет любому оператору
читать любой топик без дополнительного соглашения о схеме.

Структура кадра (big-endian):

| Поле | Тип | Размер | Описание |
|------|-----|--------|----------|
| timestamp_ns | int64 | 8 байт | Временная метка начала блока (Unix-наносекунды) |
| sample_rate_hz | int32 | 4 байта | Частота дискретизации |
| n_samples | int32 | 4 байта | Количество отсчётов в блоке |
| channel_id | int8 | 1 байт | Номер канала (0, 1, …) |
| source_id | int8 | 1 байт | Тип источника (1 = синтетика, 2 = PicoScope) |
| reserved | int16 | 2 байта | Зарезервировано (= 0) |
| samples | float32[] | 4×N байт | Массив отсчётов |

Заголовок занимает 20 байт, далее N×4 байт данных. Для операторов-статистиков
поле n_samples принимает малые значения (4 для stats, 3 для threshold) —
формат кадра не меняется.

Модуль `wave_integration.codec` предоставляет `encode_block()` и
`decode_block()`. Все операторы, генераторы и тесты работают через этот модуль.

## 3. Источники сигнала

### 3.1 Синтетический генератор (wave-gen)

CLI-инструмент `wave-gen` публикует непрерывный поток блоков в брокер.
Поддерживает три типа сигнала:

- **sine** — синусоида заданной частоты и амплитуды. Фаза сохраняется между
  блоками, поэтому при FFT не возникает артефактов на границах.
- **chirp** — линейный свип частоты от f1 до f2 Гц (каждый новый блок —
  следующий участок развёртки). Используется для демонстрации динамики спектра.
- **noise** — белый гауссовский шум заданного среднеквадратичного отклонения.
  Используется для демонстрации полосового фильтра.

Размер блока фиксирован: 4096 отсчётов при частоте дискретизации 100 кГц
(длительность блока ~41 мс). Скорость публикации задаётся параметром `--rate`
(блоков в секунду, по умолчанию 10).

При разрыве соединения с брокером генератор ждёт 2 секунды и переподключается,
сохраняя фазовый offset — сигнал продолжается непрерывно.

### 3.2 Адаптер осциллографа PicoScope (wave-osc)

CLI-инструмент `wave-osc` захватывает блоки отсчётов с реального осциллографа
PicoScope 5000a (через фирменный драйвер ps5000a.dll/so) или с программной
имитации, не требующей железа.

Параметры захвата соответствуют реальному прибору:
- **timebase** — управляет частотой дискретизации по той же формуле, что и
  hardware (timebase=8 → ~12,5 МГц в 16-битном режиме)
- **pre_samples + post_samples** — количество отсчётов до и после триггера
- **range_mv** — диапазон входного напряжения
- **coupling** — AC/DC
- **channel** — A или B

Инструмент может работать в двух режимах вывода:
- публикация в брокер (параметр `--broker`)
- запись в бинарный файл (параметр `--output-mode=bin`) — для тестирования без
  брокера

### 3.3 Абстракция CaptureSource

Оба источника (реальный и синтетический) реализуют общий интерфейс
`CaptureSource` с методами `open()`, `configure()`, `capture_block()`,
`close()`. Это позволяет `wave-osc` и GUI-адаптеру переключаться между
источниками без изменения кода захвата.

`SyntheticOscilloscopeSource` воспроизводит поведение реального прибора:
использует ту же формулу timebase, генерирует блоки нужного размера, делает
паузу на время реального окна захвата.

### 3.4 GUI-адаптер осциллографа (wave-osc-gui)

Отдельный компонент `components/osc-adapter-gui` — настольное приложение на
tkinter. Предоставляет графический интерфейс для управления захватом без
терминала:

- выбор источника: синтетика или реальный PicoScope
- настройка параметров захвата (timebase, диапазон, связь, частота кадров)
- выбор брокера и топика
- кнопки Start/Stop, лог событий, счётчик блоков и пропущенных кадров
- возможность одновременно публиковать в брокер и записывать в файл

## 4. Операторы обработки сигналов

Все операторы следуют единому контракту. Базовый класс `Operator` берёт на
себя всю работу с брокером: подключение, подписку, коммит offset'ов,
переподключение при обрывах. Наследник реализует только один метод:

```
process(record: dict) -> bytes | None
```

Если метод вернул `bytes` — результат публикуется в output-топик. Если
`None` — запись пропускается (фильтрация по условию). Оператор не хранит
состояние между вызовами — каждый блок обрабатывается независимо.

Все операторы запускаются как отдельные CLI-процессы. Параметры передаются
через аргументы командной строки. Несколько экземпляров одного типа оператора
могут работать одновременно на разных топиках.

### 4.1 FFT-оператор (wave-fft)

Читает из топика `raw.*`, вычисляет амплитудный спектр через `numpy.rfft`,
публикует в `spectrum.*`.

Результат — вектор длиной N/2+1 (для блока 4096 отсчётов → 2049 частотных
бинов). Каждый bin содержит амплитуду соответствующей частотной составляющей
(модуль комплексного значения спектра). Частотное разрешение: sample_rate / N
= 100000 / 4096 ≈ 24,4 Гц на бин.

### 4.2 Stats-оператор (wave-stats)

Читает из `raw.*`, вычисляет четыре статистики по блоку, публикует в `stats.*`.

Выходной кадр содержит 4 значения (кодируется как обычный блок с n_samples=4):
- `samples[0]` — RMS (среднеквадратичное)
- `samples[1]` — Peak (максимальное по модулю)
- `samples[2]` — Peak-to-peak (размах: max − min)
- `samples[3]` — Mean (среднее)

Используется для мониторинга уровня сигнала без визуализации осциллограммы.

### 4.3 Filter-оператор (wave-filter)

Полосовой фильтр. Читает из `raw.*`, публикует отфильтрованный сигнал той же
длины в `filtered.*`.

Реализация: numpy.rfft → обнуление бинов вне диапазона [low_hz, high_hz] →
numpy.irfft. Это идеальный прямоугольный фильтр в частотной области — 
максимально крутые края среза без итераций. Параметры передаются при запуске:
`--low-hz` и `--high-hz`.

Фильтр stateless: обрабатывает каждый блок независимо, без буферизации между
блоками.

### 4.4 Threshold-оператор (wave-threshold)

Детектор событий по уровню. Читает из `raw.*`, публикует в `events.*` только
если пиковая амплитуда блока превысила порог.

Логика: вычислить `max(|samples|)`, сравнить с `threshold_mv`. Если пик ≤
порогу — вернуть `None` (запись не публикуется). Если пик > порога —
опубликовать событие: кадр из 3 значений (peak_value, threshold, block_len).

Параметр `--threshold-mv` задаётся при запуске. Используется для оповещения о
выбросах или определения активности сигнала.

## 5. Оркестратор

Компонент `components/orchestrator` управляет жизненным циклом всего пайплайна.
Вместо запуска каждого процесса вручную пользователь описывает конфигурацию
в YAML-файле и запускает одну команду.

### 5.1 Формат конфигурации

```yaml
name: "full_pipeline"
broker: "127.0.0.1:7912"

sources:
  - name: gen_chA
    type: synth
    params:
      waveform: sine
      freq: 1000
      topic: raw.gen.chA
      rate: 10

operators:
  - name: fft_chA
    type: fft
    params:
      input_topic: raw.gen.chA
      output_topic: spectrum.gen.chA
      group_id: fft-pipeline
```

Секция `sources` — источники данных (тип `synth` или `osc`). Секция
`operators` — шаги обработки. Каждый узел имеет имя, тип и словарь параметров.

### 5.2 Управление процессами

При запуске `wave-orchestrator start` для каждого узла строится командная строка
(по реестру типов: `synth` → `wave-gen`, `fft` → `wave-fft`, и т.д.),
запускается отдельный дочерний процесс через `subprocess.Popen`. PID'ы
сохраняются в JSON-файл состояния.

Команда `stop` посылает SIGTERM всем сохранённым процессам и удаляет файл
состояния.

Команда `reload` принимает путь к новому конфигурационному файлу, останавливает
текущие процессы и запускает новые без перезапуска Docker-сервисов. Это позволяет
переключать сценарии обработки на лету.

### 5.3 HTTP API

При запуске с флагом `--serve-api` оркестратор поднимает встроенный HTTP-сервер
на порту 8099 (stdlib `http.server`, отдельный поток). API:

| Метод | Путь | Описание |
|-------|------|----------|
| GET | /status | Список процессов с PID и статусом alive/dead |
| GET | /configs | Список доступных YAML-конфигов |
| GET | /configs/{name} | Содержимое конкретного конфига |
| POST | /start | Запустить конфиг (body: `{"config": "path"}`) |
| POST | /stop | Остановить все процессы |
| POST | /reload | Перезапустить с новым конфигом |

Все ответы — JSON, заголовки CORS разрешают запросы с любого origin (нужно для
веб-интерфейса).

### 5.4 Реестр типов

Модуль `registry.py` хранит словарь соответствия: имя типа из YAML → имя
CLI-команды. Преобразует параметры с underscore в CLI-флаги с дефисом
(`input_topic` → `--input-topic`). Расширение системы новым оператором
сводится к добавлению одной строки в реестр.

Четыре готовых конфигурации для демонстрации:

## 7. Веб-интерфейс

Веб-интерфейс (React + TypeScript, субмодуль wave-ui) расширен несколькими
страницами и функциями.

### 7.1 /lab — осциллограф в реальном времени

Страница позволяет выбрать любой топик из брокера и визуализировать поток
данных. Два компонента:
- **TimeSeriesChart** — осциллограмма: значения отсчётов по времени
- **SpectrumChart** — спектрограмма: амплитуды по частоте

Пользователь выбирает тему (топик) из выпадающего списка. Данные поступают
через WebSocket или polling к HTTP API брокера.

### 7.2 /constructor — визуальный конструктор пайплайна

Страница построена на библиотеке React Flow (`@xyflow/react`). Реализует
визуальный редактор вычислительного графа:

- **NodeCard** — визуальное представление узла (источника или оператора):
  иконка, тип, входные/выходные коннекторы для рёбер
- **FormEditor** — боковая панель с формой параметров узла. При выборе
  узла в графе открывается форма с полями, соответствующими типу узла
- **SchemaEditor** — редактор YAML, показывает текущий граф в виде конфига
  оркестратора
- **NODE_CATALOGUE** — статический каталог типов узлов с описанием параметров
  каждого типа. Используется для генерации форм. Содержит все 5 типов операторов
  и тип источника synth.

Функциональность:
- Добавление узлов из каталога перетаскиванием или через панель
- Соединение узлов рёбрами (вход/выход по topic-именам)
- Экспорт графа в YAML-конфиг оркестратора
- Загрузка текущего конфига из оркестратора через API

Вкладка «Схема» на той же странице показывает живой граф запущенного пайплайна
(данные из GET /status оркестратора), отображая статус каждого процесса.

### 7.3 /topics — список топиков

Таблица всех топиков в брокере с live-обновлением: имя, число партиций,
текущий offset (количество опубликованных сообщений), список активных consumer
groups. Клик по топику открывает детальную страницу с графиком throughput.

### 7.4 /metrics — метрики пайплайна

Сводная страница: throughput по каждому топику (сообщений/сек), задержка
обработки, количество активных consumer groups. Данные берутся из HTTP API
брокера (порт 8090).

## 9. Деплой и скрипты запуска

### docker-compose.dev.yml
Для локальной разработки: только брокер (порт 7912, 8090) и UI (порт 8080).
Операторы запускаются напрямую из Python-окружения через оркестратор.

### docker-compose.demo.yml
Полный стек в контейнерах: брокер + UI + wave-gen + wave-fft + wave-stats +
wave-filter + wave-threshold + wave-fft-osc. Все Python-компоненты собираются
из одного Dockerfile.integration. Использует YAML-якоря для переиспользования
настроек сборки.

### Dockerfile.integration
Образ на python:3.11-slim. Копирует wave-python-sdk и components/integration,
устанавливает зависимости (numpy, PyYAML) и пакеты. Результат — образ с
установленными entry points: wave-gen, wave-fft, wave-stats, wave-filter,
wave-threshold, wave-osc.

### scripts/demo.sh
Принимает имя сценария (по умолчанию `full_pipeline`). Запускает Docker-сервисы
(брокер и UI), активирует Python-виртуальное окружение, запускает оркестратор
с нужным конфигом и выводит список URL. Переключение сценария — одной командой
`wave-orchestrator reload`.

### scripts/stop.sh
Graceful shutdown: сначала команда `wave-orchestrator stop` (завершает дочерние
процессы через state.json), затем `kill` по PID-файлу самого оркестратора, затем
`pkill` как страховочная сетка, затем `docker compose down`.
