# Контекст для Claude Code: Фаза 1 интеграционного слоя

## Миссия

Собрать минимальный сквозной MVP интеграционного слоя поверх готового брокера сообщений `wave-mq`. На выходе фазы: запускается стек, в браузере видна живая осциллограмма синтетического синуса и рядом — его спектр, посчитанный отдельным Python-процессом через брокер. Это MVP всего проекта; реальный осциллограф и доп. операторы будут позже, **в этой фазе их не делаем**.

Цель — *доказать, что архитектура работает end-to-end*. Не оптимизировать, не писать тесты на всё, не вылизывать API. Только пройти весь путь данных.

## Что уже есть и что НЕ трогать

Три репозитория с готовым кодом, агент должен с ними ознакомиться перед планированием:

- **`wave-mq`** (Go, <https://github.com/C4erries/wave-mq>) — брокер сообщений. Полностью готов, в эту фазу **не модифицируется**. Используется как чёрный ящик через его HTTP API (порт `:8090`), бинарный протокол (`:7912`) или MQTT (`:1883`).
- **`wave-python-sdk`** (Python, <https://github.com/C4erries/wave-python-sdk>) — клиентский SDK. Установить через `pip install wave-python-sdk`. Главный класс `WaveMQClient`, есть оба транспорта (`transport="tcp"` дефолт, `transport="http"`). Уже умеет `ensure_topic`, `produce_one`, `produce_many`, `consume_poll`, `fetch_latest`. **Используем как есть.** Если чего-то остро не хватает — добавляем в форк, не велосипедим.
- **`wave-ui`** (React + Vite, в umbrella-репозитории <https://github.com/C4erries/wave>) — админ-UI брокера. Уже есть экраны Dashboard, Topics, Topic Details, Consumer Groups, Metrics. **В Фазу 1 добавляем один новый экран** «Лаборатория» (или «Lab»), остальные не трогаем.

Запускается всё через `docker-compose.single.yml` в umbrella-репо `wave`. Этот compose должен продолжать работать; новые компоненты — отдельно (генератор и оператор запускаются как обычные Python-скрипты, либо позже подцепляются к compose).

## Архитектурные решения, уже принятые

Не нужно переосмысливать, просто следовать:

- **Один Record = один блок захвата.** В `value` лежит бинарный фрейм: заголовок (timestamp, sample_rate, n_samples, channel_id, source_id) + N × `float32` сэмплов. Конкретный байтовый формат выбирает агент: либо ручная сериализация через `struct.pack` с фиксированным header'ом, либо `msgpack` (если хочется проще). Главное — выбрать одно и зафиксировать в общем модуле, чтобы и продюсер, и оператор, и UI декодировали одинаково. Размер блока — 4096 сэмплов, sample rate — 100 кГц (значения подобрать на глаз, чтобы спектр был наглядным).
- **Имена топиков:** `raw.<source>.<channel>` для сырых сигналов, `spectrum.<source>.<channel>` для FFT. В Фазе 1 это `raw.gen.chA` и `spectrum.gen.chA`. Одна партиция, replicationFactor=1.
- **Контракт оператора:** Python-класс с атрибутами `input_topics`, `output_topics` и методом `process(record) -> list[Record]`. Stateless по умолчанию. Запускается как отдельный Python-процесс со своим consumer group. **Базовый класс — 30-50 строк, минимально.** Никаких фабрик, плагинов, DI-контейнеров. Тонкая обёртка вокруг `consume_poll` + `produce_one`.
- **Никакой кластеризации, репликации, Raft.** Single-node брокер, всё крутится локально.

## Что должно появиться в коде

Решение о размещении агент принимает сам (предлагаю новый репо `wave-integration` либо папку в umbrella). Содержательно нужны:

- `producers/synth.py` — синтетический генератор. В бесконечном цикле формирует блоки сэмплов (sine / noise / chirp — переключается через CLI-флаг или ENV), кладёт в `raw.gen.chA`. Параметры волны (частота для синуса и т.п.) — тоже из CLI.
- `operators/base.py` — базовый класс `Operator`. Минимум, не философствуем.
- `operators/fft.py` — конкретный FFT-оператор. Subscribe на `raw.gen.chA`, publish в `spectrum.gen.chA`. Внутри — `numpy.fft.rfft` плюс `np.abs`. Никаких окон Хэннинга, никаких overlapping windows — берём блок как есть.
- Общий модуль с (де)сериализацией Record.value, чтобы продюсер и оператор использовали один код.
- В `wave-ui` — новая страница «Лаборатория». Два графика рядом: time-domain (по `raw.gen.chA`) и frequency-domain (по `spectrum.gen.chA`). Получение данных — HTTP-поллинг существующего `/api/topics/...` каждые 300-500 мс. **Не добавлять SSE/WebSocket на брокер** — это запланировано на более поздние фазы.
- `README.md` в новом коде, минимальный: как запустить три компонента в правильном порядке.

## Когда фаза считается готовой

Контрольный сценарий — должен пройти без ручных правок:

1. Запускается стек брокера + UI (`docker compose -f wave/docker-compose.single.yml up`).
2. Создаются топики `raw.gen.chA` и `spectrum.gen.chA` (либо вручную через `mbctl`, либо через `ensure_topic` при старте продюсера/оператора — второе предпочтительнее).
3. Стартует `python -m ... synth --waveform=sine --freq=1000`.
4. Стартует `python -m ... fft`.
5. В браузере на UI на новой странице видны: непрерывно обновляющаяся осциллограмма (синусоида в районе указанной частоты) и спектр с чётко выраженным пиком в той же точке. Лаг 1-2 секунды допустим.
6. Переключение `--waveform=noise` на лету (рестарт продюсера) приводит к видимому шуму и плоскому спектру в UI без любых других действий.

Если эти шаги выполняются — фаза закрыта.

## Развилки, которые агент должен решить сам

Я не уверен в правильном выборе — оставляю агенту, но даю предпочтения:

- **Формат байтов Record.value:** custom `struct.pack` (компактнее, чуть больше кода) **vs** msgpack (проще, +зависимость). Я бы взял `struct.pack` с фиксированным заголовком, но msgpack тоже норм.
- **Чем рендерить графики в UI:** зависит от того, что уже используется в `wave-ui`. Если там Recharts — годится, если ничего нет — uPlot хорош для real-time time-series. Агент пусть прочтёт `wave-ui/package.json` и решит.
- **Где разместить новый код:** новый репозиторий `wave-integration` рядом с остальными **vs** папка `examples/integration/` в umbrella. Первое чище для дальнейшего роста; второе быстрее. Я склоняюсь к первому, но не настаиваю.
- **Транспорт SDK для продюсера/оператора:** TCP (бинарный протокол) **vs** HTTP. TCP эффективнее, HTTP проще диагностируется. Для Фазы 1 без разницы; рекомендую TCP по умолчанию.

## Жёсткие ограничения

- Не модифицировать Go-код `wave-mq`.
- Не вводить heavyweight-фреймворки (никаких Flink/Spark/Faust, никакого Celery, никакого Django). Только `numpy`, существующий SDK, базовая стандартная библиотека.
- Не писать кластерные тесты, не трогать Raft-режим, не использовать `-replication=true`.
- Тесты — минимум, только smoke-тест на цикл «produce → consume → decode» в общем модуле сериализации. Покрытие не цель.
- Не делать абстрактный «фреймворк операторов» с pluggable backends. Один класс, один файл, конкретный FFT.

## Порядок действий, рекомендуемый агенту

Перед составлением плана прочитать README трёх репозиториев (`wave-mq`, `wave-python-sdk`, `wave`), посмотреть `examples/python/sdk/tcp` в `wave-python-sdk` (там есть рабочие producer/consumer-сниппеты, которые точно работают), и оценить структуру `wave-ui` (как там устроены страницы, какой роутинг). После этого — план реализации, после этого код.

Если на каком-то шаге упирается в неоднозначность, которая не покрыта этим документом — *спросить, не угадывать*.
