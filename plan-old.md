Где в этой связке естественно лежит твоя курсовая

Слово «интеграционный слой» в названии перестаёт быть пустым, когда ты ставишь
его между конкретным источником (осциллом) и конкретным потребителем
(инструмент анализа). У тебя на руках:

— источник реального стримового потока (PicoScope), который сейчас закрыт сам в
себе и пишет в файлы; — транспорт (брокер wave-mq) — готов; — клиентская
сторона (SDK, UI) — готова, но без живого нагрузочного сценария.

Связав их через брокер с топиками вида «сырой сигнал / спектр / признаки» и
«модами» обработки (БПФ on-the-fly как ты предложил), ты получаешь честную
end-to-end демонстрацию интеграционного слоя — и это ровно тот сюжет, который
вытягивает абстрактное название темы во что-то осязаемое.

Про «переписать осцилл на другой язык» — стоит держать в голове, что весь нижний
слой PS5000AImports.cs — это P/Invoke в нативный SDK PicoTech (.dll). Эти DLL
официально доступны под Windows; биндинги есть для C#, C, и неофициальные для
Python (через ctypes) и LabVIEW. Полностью переписать на Python реально, но
день-два уйдёт на отладку драйвера и таймингов. C# можно оставить и просто
добавить туда сетевой паблиш в брокер — это будет самый быстрый путь.

Базовая идея, общая для всех вариантов

Брокер из прошлой курсовой превращается в транспорт, а новая работа — про то,
что лежит поверх транспорта и по краям: со стороны источника (адаптер
осцилла), со стороны обработки (операторы, преобразующие потоки), со
стороны потребителя (UI, экспорт, хранилище). Это и есть «интеграционный
слой» из названия. Сам брокер не трогаем — только используем его API.

Минимальный сквозной сценарий, который должен работать в финале:

осциллограф → топик raw.signal.chA (и B/C/D) → оператор FFT, подписанный на raw,
публикующий в spectrum.chA → UI подписан на оба и рисует и осциллограмму, и
спектр в реальном времени. Это уже честная end-to-end демонстрация: четыре
независимых компонента (источник, оператор, потребитель, транспорт), связанных
только через топики.

Дальше — что наращивать вокруг этого ядра.

Вариант A. «Композиционный конвейер потоковой обработки» (рекомендую)

Нарратив курсовой: интеграционный слой как фреймворк операторов — маленьких
Python-классов, которые подписываются на N топиков и публикуют в M других. Из
них собирается ориентированный граф обработки (DAG). «Моды» из твоей
формулировки — это просто разные конфигурации графа.

Что писать руками:

  - Адаптер осцилла — самый дешёвый путь: добавить в C#-проект клиент MQTT (есть
    библиотека MQTTnet), и из существующего цикла block-capture после захвата
    вместо записи в .txt публиковать в топик raw.signal.chN. Брокер
    MQTT-фронтенд умеет, ничего нового на стороне wave-mq писать не надо.
    Формат — простой бинарный кадр: [uint64 ts_ns][uint32 sample_rate][uint32
    n_samples][float32 × n]. Полдня.
  - Базовый класс Operator в Python поверх твоего SDK — что-то вроде class
    Operator: input_topics, output_topics, process(record) -> list[record].
    Рантайм гоняет цикл: poll → process → produce. На каждом операторе свой
    consumer group, чтобы оффсеты копились на брокере.
  - Стандартные операторы: FFT (можно прямо портировать FurieTrans.cs или взять
    numpy.fft — это два часа), MovingAverage, Decimate,
    ChannelSplit/ChannelMerge, Window (sliding/tumbling), ThresholdDetect
    (выдаёт события). Тут принципиально, что операторы не знают друг про
    друга — связь только через топики. Это и есть «интеграционный слой».
  - Декларативный конфиг — YAML, описывающий граф: какие операторы запущены,
    какие топики у них на входе/выходе, параметры (fft.window=hann,
    fft.n=8192 и т.п.). Это и есть «модовая система»: переключая конфиг, ты
    переключаешь, что в данный момент считается на лету.
  - Источник-генератор — синтетический Python-источник (синус/шум/чирп). Нужен
    обязательно: тестировать без подключённого осцилла, демонстрировать в
    защите без железа, и идейно — он подтверждает, что слой действительно
    «интеграционный» (источников больше одного).
  - Расширение UI — две карточки на дашборде: «Live time-domain» (осциллограмма)
    и «Live spectrum» (БПФ-график). Минимально — поллинг HTTP API брокера на
    свежие записи нужного топика; красиво — добавить на брокере SSE-эндпоинт
    /api/topics/{t}/stream (десяток строк в Go, переиспользует существующий
    Fetch). Рисовать в Recharts или uPlot.

Что заявляешь как вклад работы:

1.  Спроектированная архитектура слоя: модель «источник — оператор —
    потребитель», контракт топиков, разделение ответственности.
2.  Реализация операторного фреймворка с конфигурируемым графом и сменой режимов
    без перезапуска.
3.  Адаптер реального научного источника (PicoScope) и синтетического источника
    как доказательство универсальности.
4.  Расширения UI для живой визуализации.

Где «новизна» / научная часть: разбор моделей доставки (at-least-once,
идемпотентность операторов, что происходит при сбое и replay), оконных
моделей (tumbling vs sliding), особенностей привязки оператора к partition. Это
всё хорошо ложится в текст.

Почему я бы выбрал этот: ровно покрывает название курсовой («интеграционный слой
для потоковой передачи»), даёт богатую теоретическую часть (можно ссылаться на
Kafka Streams, Apache Flink, Spark Streaming как на родственников), и сразу
красиво показывается на защите.

Вариант B. «Схемо-ориентированный интеграционный слой со схема-реестром»

Нарратив: ключ интеграции — не код, а контракты данных. У тебя есть Schema
Registry (на самом брокере, в служебном топике _schemas), типизированные
сообщения, версионирование схем и кодеки. Адаптеры и операторы — это
компоненты, договаривающиеся через схемы.

Что писать:

  - Схемный язык — берёшь готовый (Protobuf или MessagePack + JSON Schema для
    метаданных) и оформляешь это как часть SDK. Сообщение в топике несёт
    хедер schema-id, по которому потребитель тянет схему из реестра.
  - Topic registry на брокере — служебный compacted-топик, где хранятся
    определения схем. По плану в wave-mq для метаданных топиков уже
    есть metadata.log, можно по аналогии сделать schemas.log (или просто
    использовать обычный compacted-топик, если у тебя compaction работает).
  - Cхемы: Waveform v1, Spectrum v1, Event v1, Stats v1. Версии: Waveform v2
    добавляет поле gain — показать обратную совместимость.
  - Адаптеры: те же два (осцилл + генератор) — но они регистрируют свои выходные
    схемы при старте.
  - Один-два оператора: FFT (Waveform → Spectrum), ThresholdEvent (Waveform →
    Event).
  - UI — список зарегистрированных схем, инспектор сообщений с автоматической
    десериализацией по schema-id.

Что заявляешь: проектирование контрактного слоя для разнородных компонентов,
реализация механизма версионирования и хранения схем, демонстрация эволюции
схемы без поломки потребителей.

Подводный камень: менее «зрелищно» на защите, чем вариант A. Текстовая часть
выходит сильнее (можно красиво писать про Avro, Confluent Schema Registry,
semver контрактов), но визуальная — слабее. Если препод любит инженерную
аккуратность — это твой вариант; если хочет «вау-демо» — вариант A.

Вариант C. «Платформа для онлайн-анализа сигналов» (UI-forward)

Нарратив: не фреймворк операторов и не схемы — а готовое прикладное приложение
для лаборатории, где брокер использован как backbone. Главное лицо работы —
UI. Это самый быстрый вариант по объёму нового кода, но самый узкий по теории.

Что писать:

  - Адаптер осцилла (MQTT, как в варианте A).
  - Один серверный воркер на Python: подписывается на raw-топик, считает
    FFT/спектрограмму/RMS/пики, публикует в производные топики. Без
    обобщённого фреймворка операторов — просто захардкоженный набор
    обработок.
  - Сильно прокачанный UI: экран «Лаборатория» с переключателем мод
    (Time/Spectrum/Spectrogram/Waterfall), сохранением сессии (запись → реплей
    через брокер с другой скоростью), сравнением двух запусков рядом. Здесь
    можно делать красивые d3/Plotly-визуализации, водопад из спектрограмм, и

использование лог-ориентированной семантики (replay, повторяемость
экспериментов) как методологическое преимущество над файловым подходом.

Кому подходит: если хочется «красиво показать» и текстовая часть тебе менее

Что важнее всего обдумать на старте

Первое — что лежит в одной записи (Record.value). Это самое фундаментальное
решение, оно влияет на всё остальное. Варианты на пальцах: либо один Record
= один полный блок захвата осцилла (например, 8192 сэмпла по 4 каналам, как
[uint64 ts][int32 sample_rate][int32 n][float32 × n]), либо Record = окно
меньшего размера, либо Record = один сэмпл (последнее — глупо, не
рассматриваем). Если запись = блок целиком, то FFT-оператор тривиален:
«один блок на входе → один спектр на выходе». Если запись = окно, нужен
отдельный оператор Window, который собирает блоки в окна. Я бы шёл по
варианту «Record = блок захвата» — он естественно соответствует тому, как
осциллограф уже работает (block capture), и оператор FFT становится stateless
one-shot. Но это развилка, на ней стоит подумать ещё раз — внизу пишу подробнее.

Второе — схема именования топиков. От неё зависит, как легко будет добавлять
новые источники, новые каналы и новых потребителей. Базовый шаблон, который
мне нравится: <стадия>.<источник>.<канал> — raw.osc.chA, spectrum.osc.chA,
raw.gen.chA. Префикс «стадия» (raw / spectrum / stats / events) сразу говорит,
что лежит в топике; «источник» (osc / gen) — кто положил; «канал» — какая
часть сигнала. Главное преимущество: ты можешь подключить второй источник
(или ещё один осциллограф) без коллизий имён, и UI/операторы могут фильтровать
через wildcard. Тут тоже есть развилка — внизу.

Третье — контракт оператора. Простейший интерфейс: оператор хранит input_topics,
output_topics, и метод process(record) -> list[record]. Этого хватает для всех
твоих случаев (FFT, Stats, Threshold). Состояние оператора — это его consumer
group offsets, которые лежат на брокере. Сам Python-процесс может
перезапускаться без потери прогресса — это ровно то, что у тебя в
SDK уже работает через consume_poll. Если на каком-то операторе появится
внутреннее состояние (например, скользящее среднее, которому нужен буфер
из последних N записей) — это state в самом операторе, и нужно думать про
checkpointing. Для курсовой я бы такие состояния просто не делал, либо делал «в
памяти, восстанавливается из чтения последних N записей при старте».

Эти три решения должны быть зафиксированы до того, как ты начнёшь писать код.

Теперь схема:Что на ней важно почувствовать:

Брокер — это не «процесс посередине», а слой топиков. На схеме две фиолетовых
полосы — это и есть брокер; всё, что соединяет источники с операторами и
операторов с UI, проходит через топики. В коде это значит, что между любыми
двумя компонентами нет прямого вызова — только publish и subscribe. Это
собственно и есть «интеграционный слой» из названия.

Операторы — это и продюсеры, и консьюмеры одновременно. Они находятся между
двумя топиковыми слоями, но это не разные сущности — это просто
Python-процессы, которые держат consumer group на raw-топиках и publish на
derived. Из этого следует крутая вещь: чтобы добавить новый оператор, не надо
менять никого. Просто запускаешь ещё один процесс, который подписался на
нужный топик и пишет в новый. UI узнает о новом топике через /api/topics и
сможет его отрисовать.

Подписка по конфигу. Серая линия между raw-топиками и операторами — это не
реальный сетевой компонент, это схематическое обозначение того, что каждый
оператор сам решает (через YAML), какие топики читать. Один и тот же
FFT-оператор может быть запущен в нескольких экземплярах с разными
конфигами: fft.osc_chA слушает raw.osc.chA, fft.osc_chB слушает
raw.osc.chB, и т.д. Через групповое имя они не конфликтуют.

Что не нарисовано — control plane. Над схемой работы данных есть отдельный слой
управления: graph.yaml (декларативное описание графа операторов) → небольшой
Python-оркестратор, который читает YAML и запускает операторов как подпроцессы
(или просто как корутины в одном процессе). «Моды», о которых ты говорил, — это
смена YAML-конфига: ты говоришь оркестратору «загрузи fft_only.yaml» или
«загрузи full_pipeline.yaml», он останавливает текущих операторов и
запускает новых. Сами топики при этом не меняются, данные продолжают
копиться. Я бы это в диаграмму не тащил — оно перпендикулярно потоку
данных и засоряет картинку. В тексте курсовой описывается отдельным
подразделом.

Сплошные стрелки vs пунктирная. events.* идёт в Archive основным путём
(сплошная) и в UI как лог уведомлений (пунктир — опциональная подписка).
Это маленький, но красивый штрих: показывает, что один и тот же топик может
иметь нескольких независимых потребителей с разными consumer group, не
мешая друг другу. Это родовое свойство log-ориентированных брокеров, и его
стоит в тексте курсовой упомянуть отдельно как преимущество над очередными
моделями.

Развилки, где я не уверен на 80%

Гранулярность топиков: канал-на-топик vs канал-в-ключе. На схеме у меня
raw.osc.chA/chB/chC/chD — отдельный топик на канал. Это даёт независимый порядок
и независимый backpressure по каналам, легко масштабируется (можно добавлять
каналы), и хорошо ложится на твою картинку с реле (один канал — один лог
измерений). Но если когда-нибудь захочешь оператор, который смотрит сразу на
все 4 канала одновременно (например, корреляции между каналами), то ему придётся
синхронизироваться между четырьмя независимыми топиками — а это нетривиально,
потому что у них разные смещения и приходят они не одновременно.
Альтернатива: один топик raw.osc, в каждой записи 4 канала вместе.
Тогда корреляции бесплатны, но добавление пятого канала или нового источника с
тремя каналами ломает схему. Я склоняюсь к канал-на-топик (60/40), потому что
для курсовой простота важнее, и корреляций ты, скорее всего, делать не
будешь. Но решение твоё — подумай, что показать на защите интереснее.

Размер записи: блок целиком vs скользящее окно. Связано с первым решением «что
лежит в Record». Если PicoScope делает block-capture по N сэмплов и кладёт это
в один Record — для FFT хорошо (один блок = один спектр). Но если потом
захочется плавную спектрограмму (с перекрывающимися окнами Хэннинга),
то блочный режим её не даст. Тут понадобится оператор Window, который собирает
блоки в перекрывающиеся окна — а это уже stateful оператор. Я бы не делал
перекрытия в первой версии (60/40 за простоту); если время останется,
добавишь оператор Window отдельно.

UI: HTTP-поллинг vs SSE-стрим с брокера. Самый простой путь — UI каждые ~500мс
делает HTTP fetch свежих записей нужного топика через существующий
/api/topics/.../messages. Работает сразу, ничего на брокере дописывать не надо,
но лаг ~500мс и сервер хаммерится каждым клиентом. Альтернатива — добавить на
брокер один эндпоинт /api/topics/{t}/stream (Server-Sent Events), который
изнутри использует Fetch+long-poll. На Go это десятки строк, переиспользует
существующий Fetch. В курсовой это отдельный плюс — «расширение брокера для
real-time потребителей». Я бы делал SSE (70/30), потому что это даёт что-то
новое заявить в работе. Но если время горит — поллинг приемлем для защиты.

Процесс-модель операторов: один процесс на всех vs процесс на оператора. Один
процесс с тред-пулом — проще запускать, проще отлаживать, но если один
оператор упал (исключение), валится весь рантайм. Процесс на оператора —
изоляция отказов, плюс реально-многоядерное исполнение (GIL не мешает), но
больше операционной сложности (надо запускать N процессов, следить за
ними). Тут я склоняюсь к single process с тредами (65/35), потому что для
курсовой защита изоляции — это уже Kubernetes-территория, а тебе нужно
показать архитектуру слоя, а не операционку.

Backpressure: догонять или прыгать в head. Если оператор тормозит — что делает?
Стандартный commit-log путь: накапливает лаг, спокойно догоняет, читает с
offset = last_committed+1 (это уже умеет SDK через consume_poll). Это правильно
для архивации и replay, но плохо для UI, который должен показывать сейчас.
Самый чистый ответ: для UI делать отдельный consumer group с правилом «при
старте fetch_latest», а не «начни с committed+1». В SDK у тебя
resolve_consume_offset и fetch_latest уже есть — это бесплатно. Я в этом уверен
на 90%, отметил скорее чтобы ты этот момент в коде учёл, когда дойдёшь.

Миссия

Собрать минимальный сквозной MVP интеграционного слоя поверх готового брокера
сообщений wave-mq. На выходе фазы: запускается стек, в браузере видна живая
осциллограмма синтетического синуса и рядом — его спектр, посчитанный
отдельным Python-процессом через брокер. Это MVP всего проекта;
реальный осциллограф и доп. операторы будут позже, в этой фазе их не
делаем.

Цель — доказать, что архитектура работает end-to-end. Не оптимизировать, не
писать тесты на всё, не вылизывать API. Только пройти весь путь данных.

Что уже есть и что НЕ трогать

Три репозитория с готовым кодом, агент должен с ними ознакомиться перед
планированием:

  - wave-mq (Go, https://github.com/C4erries/wave-mq) — брокер сообщений.
    Полностью готов, в эту фазу не модифицируется. Используется как
    чёрный ящик через его HTTP API (порт :8090), бинарный протокол (:7912)
    или MQTT (:1883).
  - wave-python-sdk (Python, https://github.com/C4erries/wave-python-sdk) —
    клиентский SDK. Установить через pip install wave-python-sdk. Главный
    класс WaveMQClient, есть оба транспорта (transport="tcp" дефолт,
    transport="http"). Уже умеет ensure_topic, produce_one, produce_many,
    consume_poll, fetch_latest. Используем как есть. Если чего-то остро не
    хватает — добавляем в форк, не велосипедим.
  - wave-ui (React + Vite, в umbrella-репозитории
    https://github.com/C4erries/wave) — админ-UI брокера. Уже есть экраны
    Dashboard, Topics, Topic Details, Consumer Groups, Metrics. В Фазу 1
    добавляем один новый экран «Лаборатория» (или «Lab»), остальные не
    трогаем.

Запускается всё через docker-compose.single.yml в umbrella-репо wave. Этот
compose должен продолжать работать; новые компоненты — отдельно (генератор и
оператор запускаются как обычные Python-скрипты, либо позже подцепляются к
compose).

Архитектурные решения, уже принятые

Не нужно переосмысливать, просто следовать:

  - Один Record = один блок захвата. В value лежит бинарный фрейм: заголовок
    (timestamp, sample_rate, n_samples, channel_id, source_id) + N × float32
    сэмплов. Конкретный байтовый формат выбирает агент: либо ручная
    сериализация через struct.pack с фиксированным header'ом, либо
    msgpack (если хочется проще). Главное — выбрать одно и зафиксировать в общем
    модуле, чтобы и продюсер, и оператор, и UI декодировали одинаково. Размер
    блока — 4096 сэмплов, sample rate — 100 кГц (значения подобрать на глаз,
    чтобы спектр был наглядным).
  - Имена топиков: raw.<source>.<channel> для сырых сигналов,
    spectrum.<source>.<channel> для FFT. В Фазе 1 это raw.gen.chA и
    spectrum.gen.chA. Одна партиция, replicationFactor=1.
  - Контракт оператора: Python-класс с атрибутами input_topics, output_topics и
    методом process(record) -> list[Record]. Stateless по умолчанию.
    Запускается как отдельный Python-процесс со своим consumer group.
    Базовый класс — 30-50 строк, минимально. Никаких фабрик, плагинов,
    DI-контейнеров. Тонкая обёртка вокруг consume_poll + produce_one.
  - Никакой кластеризации, репликации, Raft. Single-node брокер, всё крутится
    локально.

Что должно появиться в коде

Решение о размещении агент принимает сам (предлагаю новый репо wave-integration
либо папку в umbrella). Содержательно нужны:

  - producers/synth.py — синтетический генератор. В бесконечном цикле формирует
    блоки сэмплов (sine / noise / chirp — переключается через CLI-флаг или
    ENV), кладёт в raw.gen.chA. Параметры волны (частота для синуса и т.п.) —
    тоже из CLI.
  - operators/base.py — базовый класс Operator. Минимум, не философствуем.
  - operators/fft.py — конкретный FFT-оператор. Subscribe на raw.gen.chA,
    publish в spectrum.gen.chA. Внутри — numpy.fft.rfft плюс np.abs. Никаких
    окон Хэннинга, никаких overlapping windows — берём блок как есть.
  - Общий модуль с (де)сериализацией Record.value, чтобы продюсер и оператор
    использовали один код.
  - В wave-ui — новая страница «Лаборатория». Два графика рядом: time-domain (по
    raw.gen.chA) и frequency-domain (по spectrum.gen.chA). Получение данных —
    HTTP-поллинг существующего /api/topics/... каждые 300-500 мс. Не добавлять
    SSE/WebSocket на брокер — это запланировано на более поздние фазы.
  - README.md в новом коде, минимальный: как запустить три компонента в
    правильном порядке.

Когда фаза считается готовой

2.  Создаются топики raw.gen.chA и spectrum.gen.chA (либо вручную через mbctl,

4.  Стартует python -m ... fft.
5.  В браузере на UI на новой странице видны: непрерывно обновляющаяся

=== Архитектура: схема данных ===

Поток данных: источники (адаптер осциллографа на C# или Python-генератор) публикуют 
блоки сэмплов в топики raw.<источник>.<канал>. Шаблон именования всех топиков: 
<стадия>.<источник>.<канал>, где стадия = raw|spectrum|stats|events, источник = 
osc|gen, канал = chA|chB|chC|chD.

Операторы — это отдельные Python-процессы, каждый в своей consumer group; они 
читают raw.* топики, обрабатывают записи и публикуют в derived-топики (spectrum.*, 
stats.*, events.*). Потребители (UI, опциональный архив) подписываются на derived-
топики как независимые consumer groups, не мешая друг другу и не мешая операторам.

Формат одной записи (Record.value, бинарный):
- timestamp_ns: int64
- sample_rate_hz: int32
- n_samples: int32
- channel_id: int8
- source_id: int8
- payload: float32 × n_samples

Размер блока — 4096 сэмплов, sample rate — 100 кГц.

Промпт E2. Базовый класс оператора + оператор FFT

   Файл: wave_integration/operators/base.py

     - output_topics: list[str]  (для документации, не используется логикой)

     - бесконечный цикл consume_poll по input_topics с group_id
     - для каждой записи: decode_block → process → produce каждой выходной пары
     - корректный shutdown по Ctrl-C
     - логирование каждой N-ной записи (N=100)

     --group-id       (default: fft-gen-chA)
     --broker         (default: 127.0.0.1:7912)

     - извлекает массив сэмплов из записи
     - вычисляет БПФ: spectrum = np.abs(np.fft.rfft(samples))
     - сохраняет sample_rate из входной записи (нужен UI для частотной оси)
     - формирует выходную "запись" через codec.encode_block, но в payload 
       теперь спектр (амплитуды), а n_samples = len(spectrum)
     - возвращает [(output_topic, encoded_bytes)]

   топики). channel_id и source_id наследуем из входной записи.

   Только rfft + abs.

   Реализуй две функции:
   
     def encode_block(
         timestamp_ns: int,
         sample_rate_hz: int,
         channel_id: int,
         source_id: int,
         samples: np.ndarray,  # dtype=float32
     ) -> bytes
     
     def decode_block(data: bytes) -> dict
       # возвращает: {
       #   "timestamp_ns": int,
       #   "sample_rate_hz": int,
       #   "n_samples": int,
       #   "channel_id": int,
       #   "source_id": int,
       #   "samples": np.ndarray (dtype=float32),
       # }
   
   Бинарный формат (BIG-ENDIAN везде):
     int64  timestamp_ns       offset 0
     int32  sample_rate_hz     offset 8
     int32  n_samples          offset 12
     int8   channel_id         offset 16
     int8   source_id          offset 17
     int16  reserved (=0)      offset 18
     float32[n_samples]        offset 20, по 4 байта на сэмпл
   
   Используй struct.pack/unpack с форматом '>qiibbh' для заголовка (q=int64, 
   i=int32, b=int8, h=int16; '>' = big-endian).
   
   Для payload: после распаковки заголовка, прочитай оставшиеся n_samples × 4 
   байт и сконвертируй в numpy.ndarray через np.frombuffer(..., dtype='>f4').astype('<f4') 
   — это даёт правильный массив на little-endian-машине. Аналогично на 
   encode-стороне: samples.astype('>f4').tobytes().
   
   Защиты:
   - encode_block: проверь dtype samples == float32, иначе TypeError.
   - decode_block: если len(data) < 20 → ValueError, если n_samples × 4 + 20 != 
     len(data) → ValueError с понятным сообщением.

3. synth.py — синтетический генератор.
   
   CLI через argparse:
     --waveform   sine|noise|chirp                    default: sine
     --freq       Гц, для sine                        default: 1000.0
     --chirp-f1   Гц, начальная частота для chirp     default: 100.0
     --chirp-f2   Гц, конечная частота для chirp      default: 5000.0
     --amplitude                                      default: 1.0
     --noise-std  стандартное отклонение для noise    default: 0.3
     --topic      имя топика                          default: raw.gen.chA
     --rate       блоков в секунду                    default: 10
     --broker     адрес TCP                           default: 127.0.0.1:7912
     --duration   секунд, -1 = бесконечно             default: -1
     --channel-id                                     default: 0
     --source-id                                      default: 1
   
   Константы блока: N_SAMPLES=4096, SAMPLE_RATE_HZ=100_000.
   
   Логика main():
   - Парс CLI.
   - Создать WaveMQClient(args.broker, transport="tcp") как context manager.
   - client.ensure_topic(args.topic, partitions=1, replication_factor=1).
   - Завести «фазу» phase_offset_samples = 0 — это глобальный счётчик 
     произведённых сэмплов от начала запуска. Используется для непрерывной 
     синусоиды между блоками (без скачков фазы на границе).
   - В цикле:
     * сгенерировать массив из N_SAMPLES сэмплов в зависимости от waveform:
       - sine: amplitude * sin(2π × freq × t), где t = (phase_offset_samples + 
         np.arange(N_SAMPLES)) / SAMPLE_RATE_HZ
       - noise: np.random.normal(0, noise_std, N_SAMPLES)
       - chirp: использовать scipy.signal.chirp ИЛИ ручную формулу 
         f(t) = f1 + (f2-f1) × t/T, и затем sin(2π × ∫f dt). Если хочется 
         без scipy — ручная формула проще, scipy в зависимостях не указан.
     * dtype = float32 обязательно.
     * timestamp_ns = time.time_ns() — момент перед публикацией.
     * data = encode_block(...).
     * client.produce_one(args.topic, data, key=None, content_type="application/octet-stream").
     * phase_offset_samples += N_SAMPLES.
     * Логи: первый блок (с offset) — обязательно. Затем каждый 100-й.
       Формат: f"[synth] published topic={topic} offset={r.base_offset} 
       waveform={waveform} blocks={n}".
     * Спать time.sleep(1.0 / args.rate) для выдерживания темпа. Не пытайся 
       компенсировать дрейф через monotonic — для нашей цели не критично.
     * Корректно обрабатывать KeyboardInterrupt: выйти из цикла, дать 
       клиенту закрыться в context manager.
   
   Подсказка по produce_one: после твоей проверки SDK ты будешь знать, 
   принимает ли он bytes. Если нет — оберни через

       запуск; если group новая — с начала, это поведение SDK по умолчанию для 
       "committed")
     * max_messages=max_messages_per_poll
     * poll_interval=poll_interval
     * commit=True  (offset коммитится после успешной обработки)
     * on_record=self._on_record_callback
     * stop_when_caught_up=False  (бесконечный цикл)
   - _on_record_callback(record_obj):
     * record_obj.value — это bytes (если SDK возвращает bytes) или base64-строка 
       (если в SDK для TCP идёт base64-обёртка — ПРОВЕРЬ это, как и в E1).
     * Если value — bytes, передаём в codec.decode_block(value).
     * Если строка с префиксом "base64:" — убираем префикс и base64-декодируем.
     * Вызвать self.process(decoded_record).
     * Если результат не None — publish через client.produce_one_to_partition(
         output_topic, 0, result_bytes, content_type="application/octet-stream"
       ).
     * Инкрементировать n_processed. Логировать каждый 50-й.
   - KeyboardInterrupt должен выходить чисто (флаг stop, прерывание цикла, 
     finally — клиент закрыт через context manager).

   ПРИНЦИПЫ:
   - Stateless. Никаких внутренних буферов, никакого внутреннего состояния 
     между вызовами process. Состояние — только в смещениях consumer group, 
     которые брокер хранит сам.
   - Если process бросает исключение — лог уровня ERROR с трейсбэком, но цикл 
     продолжается со следующей записи. НЕ блокируем consumer group из-за одной

     осознанно жертвуем строгостью ради устойчивости. Запиши это в комментарий 
     в base.py.)
   - Размер base.py — целевой 70-90 строк включая docstrings. Если больше —

2. fft_op.py — конкретный FFT-оператор.

   Подкласс Operator. Класс FFTOperator с переопределённым process():

     class FFTOperator(Operator):
         def process(self, record_in: dict) -> Optional[bytes]:
             samples = record_in["samples"]   # np.ndarray float32, len=4096
             sample_rate = record_in["sample_rate_hz"]
             
             # БПФ амплитудный
             spectrum = np.abs(np.fft.rfft(samples)).astype(np.float32)
             # длина spectrum = n_samples // 2 + 1 = 2049 для входа 4096
             
             return codec.encode_block(
                 timestamp_ns=record_in["timestamp_ns"],  # сохраняем исходный
                 sample_rate_hz=sample_rate,              # ИСХОДНЫЙ sample rate
                 channel_id=record_in["channel_id"],
                 source_id=record_in["source_id"],
                 samples=spectrum,
             )

   ВАЖНО про sample_rate в выходном фрейме:
   - В spectrum-фрейме храним ИСХОДНЫЙ sample_rate_hz (тот же, что был на raw).
   - UI потом сможет посчитать ось частот как:
       freq[k] = k * sample_rate / (2 * (n_samples - 1))
     где n_samples — длина spectrum-массива (2049). Это даёт диапазон 
     0..sample_rate/2 = 0..50 кГц, что и есть Найквист от 100 кГц.
   - НЕ переписывай sample_rate в spectrum-фрейме под что-то другое 
     (например, под разрешение по частоте). Это нарушит формат и UI 
     неправильно отрисует ось.

   main() через argparse:

     --output-topic   default: spectrum.gen.chA
     --group-id       default: fft-gen-chA
     --broker         default: 127.0.0.1:7912

   В main() — создать FFTOperator, вызвать .run().

   НЕ ДЕЛАТЬ:
   - Никаких окон Хэннинга, Хэмминга, Блэкмана. Прямоугольное окно по 
     умолчанию (= ничего не делать).

         sample_rate = 100_000

             "timestamp_ns": 0,

             "channel_id": 0,
             "source_id": 1,

             "samples": samples,

ФОРМАТ ДАННЫХ, КОТОРЫЕ ПРИХОДЯТ ИЗ HTTP API:

GET /api/topics/raw.gen.chA/messages?offset=<N>&limit=1 возвращает JSON:
{
  "messages": [
    {
      "offset": ...,
      "partition": 0,
      "timestamp": ...,
      "key": null,
      "value": "base64:<base64-encoded бинарный фрейм>",
      "contentType": "application/octet-stream"
    }
  ],
  "highWatermark": ...,
  "nextOffset": ...
}

Префикс "base64:" нужно отрезать, остаток декодировать base64 в Uint8Array, 
после чего парсить бинарный фрейм (см. формат ниже).

БИНАРНЫЙ ФОРМАТ ФРЕЙМА (точно как в integration/src/wave_integration/codec.py):

  offset 0   int64  timestamp_ns       (big-endian)
  offset 8   int32  sample_rate_hz     (big-endian)
  offset 12  int32  n_samples          (big-endian)
  offset 16  int8   channel_id
  offset 17  int8   source_id
  offset 18  int16  reserved           (=0, big-endian)
  offset 20  float32[n_samples]        (big-endian, по 4 байта)

ВНИМАНИЕ К BIG-ENDIAN. JS DataView по умолчанию big-endian для get*() — 
параметр littleEndian опускаем или передаём false. Float32Array нельзя 
напрямую читать big-endian из ArrayBuffer — придётся читать по одному через 
DataView.getFloat32(offset, false) в цикле, либо byte-swap.

JS не имеет нативного int64. Для timestamp_ns используй BigInt: 
new DataView(buf).getBigInt64(0, false). Можно конвертировать в Number для 
отображения секунд (timestamp_ns / 1_000_000_000), но в самом коде хранить 
как BigInt.

Что в отчёте критично

Файлы как замена Save2File. Ты правильно ставишь требование. Лаборатория годами
работает через .txt от старой программы (есть MATLAB-скрипты для пост-обработки
и т.д.). Если Python-адаптер тоже умеет сваливать в файлы — он становится
drop-in заменой существующего workflow, а публикация в брокер — это
дополнительный канал. Это сильный архитектурный аргумент защиты:
«адаптер совместим с существующими процессами лаборатории». Плюс это отлично
работает как fallback для тестов: запустил → создал файл → проверил содержимое
глазами.

RatioMode.None и двойной буфер. Агент верно подметил, что C#-код суммирует
maxBuffer + minBuffer, хотя при RatioMode.None они идентичны. То есть masA = 2 ×
ADC, и потом в mult стоит компенсирующее × 0.5. Это рабочая идиома лаборатории,
и я предлагаю воспроизвести её точно в Python-адаптере. Не потому что она
«правильная», а потому что если ты получишь те же значения, что
C#-программа выдавала годами — никаких споров «а у вас амплитуды не
такие, как мы привыкли» на защите не будет.

Возможная ошибка масштабирования (×2 vs ×1). Агент это отметил: inputRanges =
±RANGE, но в формуле mult = 1/2/2 × RANGE/65536 фактический диапазон получается
±RANGE/2, то есть в 2 раза меньше заявленного. Это либо ошибка в исходном
C#-коде, либо специфика того, как они хотели представлять данные. В
Python-адаптере точно воспроизводим C#-формулу. Если это ошибка — она такая
же, как у лаборатории, и сравнимая с их данными. В курсовой это можно отдельно
обсудить как «совместимость с существующим методом обработки».

Callback vs polling. Агент прав — в Python используем ps5000aIsReady()-polling.
Проще, не нужен CFUNCTYPE, нет проблем с GIL.

Параметры захвата у них зверские: 100000 сэмплов при 62.5 MHz = 1.6 мс окно. Это
в 24 раза больше наших синтетических 4096. UI с 400-мс поллингом будет
показывать последний из ~250 блоков — это нормально, но имей в виду,
что данные будут пролетать. Это нормально для научного использования (всё в
брокере, потом анализируешь), но для демонстрации в UI на защите есть смысл
иметь возможность снизить sample rate, чтобы блоки шли в режиме «один блок раз
в 100-200 мс» и UI рисовал плавно. Поэтому в CLI должна быть возможность задать
timebase повыше (например, tb=108 даёт ~600 kHz, что при 100000 сэмплов даёт
окно ~170 мс — каждый блок виден).

Ответы на вопросы агента

1.  Канал и coupling — конфигурируемо через CLI. --channel A (default),
    --coupling AC (default). Не хардкодим.

2.  Диапазон по умолчанию — 1 V (index 6). Это «безопасный» диапазон для
    большинства тестовых сигналов, не зашкаливает в обе стороны.

3.  Timebase по умолчанию — 8 (12.5 MHz). Не 4 как в C#. С 100000 сэмплов это
    даст окно 8 мс, что нормально, и поможет UI не задыхаться. Если кому-то
    надо «как было в C#» — задаст --timebase 4 руками.

4.  BW-фильтр 20 МГц — флаг CLI --bw-filter (default off). Как опция.

5.  Модель PicoScope — отметить в README как «5000a series», без указания
    конкретного subtype. В коде использовать OpenUnit(null, ...), как в
    C#.

6.  udev rules — добавить в README, не в код. Это операционная задача установки,
    не функционал адаптера.

Архитектурное решение

Вариант А (чистый с абстракцией). Без вариантов — потому что test-mode без
железа должен быть first-class, не «костыль на флаг», а полноценный
alternative source.

Один важный момент: не создавать отдельный пакет picoscope-adapter/. Это будет
ещё один источник в той же integration/, по аналогии с wave-gen. Структура
должна быть:

integration/src/wave_integration/sources/
├── __init__.py
├── base.py          # CaptureSource ABC
├── synthetic.py     # SyntheticSource (test-mode)
└── picoscope.py     # PicoScopeSource (реальное железо)

integration/src/wave_integration/producers/
├── synth.py         # ← уже есть (wave-gen)
└── osc.py           # ← новый CLI: wave-osc, использует CaptureSource

То есть wave-osc — это тонкий entry-point, который принимает CLI-флаг
--source=real|synth|... и выбирает соответствующий CaptureSource. Это позволит в
будущем легко добавить третий источник (например, симулятор записанного файла)
без правки wave-osc.

И ещё — producers/synth.py (wave-gen) уже существует для бесконечной синтетики.
Это другой случай: там нет привязки к контракту CaptureSource, там просто
бесконечный генератор. Не сливай их. wave-gen остаётся как «прямой
генератор для интеграционного слоя в чистом виде», wave-osc
--source=synth — это «адаптер осциллографа в test-mode, имитирующий поведение
реального устройства» (включая параметры типа range, timebase). Разные
сценарии, разные роли.

КОНТЕКСТ И РЕШЕНИЯ.

Создаём в существующей integration/ новый компонент — Python-адаптер 
осциллографа PicoScope 5000a. Это самостоятельный продьюсер, по образцу

от реального устройства (или от его test-mode имитации), повторяя 
параметризацию C#-программы PS5000ABlockCapture.

генератор сигналов для общей синтетики. wave-osc — это адаптер 
осциллографа со своим API, своими параметрами устройства (range, 
coupling, timebase), своим CLI.

1. integration/src/wave_integration/sources/base.py.

   Импорты: abc, dataclasses, numpy.
   
   Dataclass для одного блока захвата:
   
     @dataclass
     class CaptureBlock:
         samples_mv: np.ndarray   # float32, длина n_samples, единицы — милливольты
         sample_rate_hz: int
         timestamp_ns: int        # момент завершения захвата (DateTime.UtcNow эквивалент)
         channel_id: int
         range_mv: int            # фактический диапазон (для документации/логов)
   
   Dataclass для конфигурации захвата (общая для real и synthetic):
   
     @dataclass
     class CaptureConfig:
         timebase: int = 8           # PicoScope timebase, default 8 (~12.5 MHz)
         pre_samples: int = 5000
         post_samples: int = 95000
         range_mv: int = 1000        # 1V default
         coupling: str = "AC"        # "AC" or "DC"
         channel: str = "A"          # "A" (на этом этапе только канал A)
         bw_filter_20mhz: bool = False
   
   ABC:
   
     class CaptureSource(ABC):
         @abstractmethod
         def open(self) -> None: ...
         @abstractmethod
         def configure(self, config: CaptureConfig) -> None: ...
         @abstractmethod
         def capture_block(self) -> CaptureBlock: ...
         @abstractmethod
         def close(self) -> None: ...
         def __enter__(self): self.open(); return self
         def __exit__(self, *exc): self.close()
   
   КЛЮЧЕВОЕ: configure() вызывается ОДИН РАЗ после open(). capture_block() 
   вызывается в цикле и возвращает один блок. Это контракт, на нём держится 
   архитектура.

2. integration/src/wave_integration/sources/synthetic.py.

   class SyntheticOscilloscopeSource(CaptureSource).
   
   Имитирует поведение PicoScope, но без железа. Что генерирует:
   
   - В open(): ничего, можно просто залогировать "Synthetic source opened".
   - В configure(): сохраняет config. Вычисляет sample_rate из timebase 
     по формуле PicoScope для 16-bit (та же что в C#): 
       dt = (timebase - 3.0) / 62_500_000.0  если timebase >= 3
       sample_rate = 1.0 / dt
     Это даёт sample_rate, реалистично соответствующий тому, что выдал бы 
     реальный осцилл при том же timebase. n_samples = pre + post.
   - В capture_block():
     * Генерирует тестовый сигнал. Параметры из ENV-переменных или 
       конструктора (waveform, freq, amplitude — см. ниже про CLI).
     * Базовая логика как в wave-gen: sine с непрерывной фазой между блоками, 
       либо noise (gauss), либо chirp.
     * Амплитуда сигнала в милливольтах в диапазоне примерно [-range_mv/2, 
       +range_mv/2], как в реальном осцилле.
     * Добавляет небольшой шум (стандартное отклонение ~0.5% от range_mv), 
       чтобы выглядело реалистично.
     * timestamp_ns = time.time_ns().
     * Имитирует длительность захвата через time.sleep(actual_capture_time), 
       где actual_capture_time = n_samples / sample_rate. Это критично — без 
       sleep блоки будут литься со скоростью CPU, и UI/брокер захлебнётся.
     * Возвращает CaptureBlock.
   - Параметры тестового сигнала: waveform, freq, amplitude — задаются в 
     __init__ конструктора, не в configure (это не параметры захвата, это 
     параметры имитации источника).
   - close(): ничего.

3. integration/src/wave_integration/sources/picoscope.py.

   class PicoScopeSource(CaptureSource).
   
   ИСПОЛЬЗУЕТ pip-пакет picosdk (надо добавить в pyproject.toml как опциональную 
   зависимость, чтобы пользователи без железа могли ставить integration без 
   тяжёлых драйверов).
   
   В pyproject.toml добавь:
     [project.optional-dependencies]
     picoscope = ["picosdk>=1.1"]
     dev = ["pytest"]
   
   Установка с поддержкой PicoScope: pip install -e ".[picoscope]"
   
   В коде picoscope.py сделай try/except на импорт picosdk на верхнем уровне, 
   и если его нет — внятная ошибка в open(): "PicoScope SDK not available. 
   Install with: pip install wave-integration[picoscope]".
   
   Логика, точно повторяющая C#:
   
   - open(): 
     * import picosdk.ps5000a as ps
     * c_handle = ctypes.c_int16()
     * status = ps.ps5000aOpenUnit(byref(c_handle), None, PS5000A_DR_16BIT)
     * Обработка PICO_POWER_SUPPLY_NOT_CONNECTED через ChangePowerSource 
       (как в C#).
     * Сохранить handle.
   
   - configure(config):
     * ps5000aSetChannel(handle, channel='A', enabled=1, coupling=config.coupling, 
       range=mv_to_range_enum(config.range_mv), analogOffset=0.0)
     * Все остальные каналы (B, C, D) — disabled.
     * Опциональный BW-фильтр через ps5000aSetBandwidthFilter, если 
       config.bw_filter_20mhz.
     * Триггер: ps5000aSetSimpleTrigger с теми же параметрами что в C#:
         enable=1, channel=External, threshold=20000, direction=Rising, 
         delay=0, autoTrigger_ms=22222
     * GetTimebase2 для определения фактического sample rate:
         intervalNs = c_float()
         maxSamp = c_int32()
         ps5000aGetTimebase2(handle, config.timebase, total_samples, 
                             byref(intervalNs), byref(maxSamp), 0)
         self._sample_rate_hz = int(round(1e9 / intervalNs.value))
     * Заранее аллоцировать ctypes-буферы для max и min:
         self._buf_max = (c_int16 * total_samples)()
         self._buf_min = (c_int16 * total_samples)()
         ps5000aSetDataBuffers(handle, 'A', self._buf_max, self._buf_min, 
                                total_samples, 0, RATIO_MODE_NONE)
     * Сохранить config, range_mv, n_samples (pre+post), self._range_mv.
   
   - capture_block():
     * ps5000aRunBlock(handle, pre_samples, post_samples, timebase, 
                      byref(timeIndisposed), 0, None, None)
       (Callback не используем — None.)
     * Polling: while True: ps5000aIsReady(handle, byref(ready)); 
                if ready.value: break; time.sleep(0.001)
     * downSampleRatio=1, RATIO_MODE_NONE:
         n_returned = c_uint32(total_samples)
         overflow = c_int16()
         ps5000aGetValues(handle, 0, byref(n_returned), 1, RATIO_MODE_NONE, 
                           0, byref(overflow))
     * ps5000aStop(handle)
     * Преобразование ADC → мВ, ТОЧНО ПО C#-формуле:
         mult = 1.0 / 2.0 * range_mv / 65536.0
         max_arr = np.ctypeslib.as_array(self._buf_max)
         min_arr = np.ctypeslib.as_array(self._buf_min)
         summed = (max_arr.astype(np.int64) + min_arr.astype(np.int64))
         samples_mv = (summed * mult).astype(np.float32)
       Это даёт сэмплы в милливольтах, БИТ В БИТ как C#-программа.
     * timestamp_ns = time.time_ns()  (момент после capture)
     * Возвращает CaptureBlock(samples_mv, self._sample_rate_hz, 
                                 timestamp_ns, channel_id=0, range_mv=range_mv)
   
   - close(): ps5000aCloseUnit(handle).
   
   КРИТИЧНО: Все вызовы picosdk оборачивай в проверку status. Если != PICO_OK 
   — поднимай PicoScopeError(status, function_name). Сделай простой класс 
   ошибки для этого.

Идея сильная для курсовой, но не для этой курсовой. Объясню.

Топик _system.events или _system.logs, в который пишут все компоненты (адаптер,
операторы, оркестратор), а UI читает и красиво показывает — это отдельный

Но за оставшееся время это: — требует протокола сообщений (структура поля

форматированием, — и не закрывает ни одной проблемы текущей демонстрации.

Приоритет 5: Оркестратор и YAML-режимы (бывший E4)

Это та архитектурная сильная сторона, которую я предлагал делать. Сейчас, когда
у тебя уже два источника (wave-gen и wave-osc), идея режимов получает
дополнительный смысл: YAML описывает «какой источник запустить, какие
операторы подключить». Скажем, режим "lab-demo" запускает wave-osc
--source=synth + wave-fft; режим "raw-only" запускает wave-osc без операторов;
режим "multi-channel-test" запустит два wave-osc на разные каналы.

Но в условиях дефицита времени это можно перенести в направления развития наряду
с топиком ошибок. Альтернатива оркестратору — просто bash-скрипт demo.sh,

демонстрации он выглядит так же эффектно («одна команда поднимает весь стек»),
но не требует кода. В курсовой это legitimate solution для прототипа.
